# 马拉松路线质量与 Web 交互优化设计

## 目标

在武汉道路矢量网络上生成可用于赛事方案评审的全程马拉松候选路线，并重构 Web 工作台，使用户可以清楚地设定起终点、选择选型目标、生成路线、查看合规结论和比较候选线。

任何选型目标只能影响通过质量闸门后的排序，不得放宽距离、路网贴合、道路重复、自交、折返、起终点间距或地形约束。系统输出是规划辅助成果，不替代 World Athletics/AIMS 认证测量。

## 规则依据与产品口径

- 标准距离为 42.195 km。
- 起终点理论直线距离不得超过 21.0975 km，即比赛距离的 50%。
- 起点到终点的净下降不得超过 42.195 m，即 1 m/km。
- 规划里程接受区间为 42.195–42.237 km。上限对应 0.1% 的短程预防余量，避免生成短于标准距离的方案；页面仍显示标准目标 42.195 km。
- 路线应位于铺装道路、适合比赛的自行车道或步道上。未知或明确不适合比赛的道路不进入候选集。
- 正式赛事距离应由合资格测量员沿运动员可跑的最短线测量并认证；规划结果中必须保留该提示。

规则来源：

- [World Athletics 2026 Competition and Technical Rules](https://worldathletics.org/download/download?filename=9bc01db7-f30e-4929-8888-c3db9016f3ed.pdf&urlslug=C1.1+%26+C2.1+-+Competition+Rules+%26+Technical+Rules)
- [World Athletics Certified Road Events](https://worldathletics.org/records/certified-roadevents)

## 选型目标

保留三个容易理解且业务区别明确的目标：

1. **竞速平坦**：在合规路线中优先低累计爬升、少急弯、少窄路、主干道路连续。
2. **组织保障**：在合规路线中优先医疗、补给、公共交通和集散可达性。
3. **城市体验**：在合规路线中优先地标、滨水、公园和观赛展示价值，同时不牺牲硬约束。

旧的“综合平衡、大众完赛、跨江风景”等六个目标合并为以上三类，减少选择负担。已有路线评分字段可以继续复用，但需提供兼容映射，避免影响存量测试和数据。

## 路线质量闸门

路线只有在以下检查全部通过时才可进入 UI 候选列表：

| 检查 | 通过条件 |
|---|---|
| 里程 | 42.195–42.237 km |
| 起终点间距 | ≤ 21.0975 km |
| 起终点净下降 | ≤ 42.195 m |
| 累计爬升 | ≤ 180 m |
| 单段绝对坡度 | ≤ 5%，桥梁等数据异常段需要可信高程数据后才能放行 |
| 连续大坡 | 绝对坡度 > 3% 的连续距离 ≤ 1 km |
| 道路重复 | 同一物理道路边使用次数不超过一次，重复比例为 0 |
| 即时折返 | 不允许沿上一条物理道路反向返回 |
| 自交 | 非相邻线段几何相交数为 0 |
| 局部绳结 | 1.25 km 窗口内不得回到 160 m 邻域形成小环或毛刺 |
| 路网连续 | 相邻道路边端点误差 ≤ 10 m |
| 路网贴合 | 输出坐标必须逐点来自所选道路边的真实几何，不插入跨路直线 |
| 道路适赛性 | 所有道路边均通过道路等级、铺装/用途和禁行检查 |

地形数据覆盖不足时，不伪造“通过”结论。系统应将路线标记为“地形数据不足”并淘汰，不得把缺失值或开发测试替代值当作零坡度。

## 算法方案比较

### 方案 A：继续修补随机游走

在现有贪心随机游走中增加更多惩罚与重试。改动较小，但随机路径容易走入死胡同，长度微调困难，规则越多越容易出现“有结果但不合规”的情况，不采用。

### 方案 B：约束感知 Beam Search + 闭合下界 + 局部修复（采用）

使用有界 Beam Search 扩展简单路径；每次扩展都禁止复用物理道路边、即时折返和新自交，并用到终点的最短可行距离作为闭合下界进行剪枝。接近目标距离后，用 k 条无重复边的闭合路径尝试完成；对长度略有偏差的候选，仅允许用不与既有路线冲突的替代子路径做局部修复。该方案可解释、可测试，不需要引入大型求解器，适合当前 TypeScript 前端和武汉路网规模。

### 方案 C：MILP/CP-SAT 全局优化

把道路选择、流平衡和距离写成整数规划。理论上约束表达完整，但依赖重、浏览器端性能和调参风险高，且几何自交与局部坡度仍需外部校验，本轮不采用。

## 算法架构

### 1. 图预处理

- 将正反向边归一到同一 `physicalEdgeId`。
- 保留道路原始几何，而不是只保留首尾节点。
- 计算道路适赛性、长度、方向坡度、道路等级、POI 贡献和阻力。
- 对起终点执行带最大吸附距离的节点吸附；超出阈值时返回明确错误。
- 预计算终点反向最短距离，用于 Beam Search 可达性与剩余里程剪枝。

### 2. 候选搜索

搜索状态包含当前节点、节点序列、物理边集合、长度、累计爬升、连续大坡距离、几何索引和目标得分。扩展时先执行硬约束，再计算目标相关的软分数。Beam 保留一组多样状态，并按当前位置、已用边摘要和长度桶去重。

剪枝条件包括：

- 当前长度超过 42.237 km；
- 当前长度加终点最短距离超过 42.237 km；
- 即使走可达上界也无法达到 42.195 km；
- 新边造成重复、折返、自交、局部绳结、坡度或适赛性违规；
- 起终点间距本身超过上限。

### 3. 闭合与长度修复

当剩余里程进入闭合窗口时，搜索若干条不复用既有物理边的终点路径。若成品长度位于规划区间内，进入质量闸门；若轻微偏离，只允许替换一段为合法的平行绕行路径。禁止用“直接连线”、反向重复道路或同一路段往返补里程。

### 4. 多目标排序

候选先通过统一质量闸门，再分别计算三个目标分数。目标切换只重新排序，不重新定义“合格”。输出最多三条候选，并增加候选间道路重合惩罚，避免三个结果几乎相同；候选之间可以共享必要主干道路，但单条路线内部不得重复。

### 5. 失败返回

找不到合格路线时返回结构化失败原因，如“起终点间距超限”“可用路网不足以形成 42.195 km 简单路径”“坡度约束淘汰全部候选”。UI 不展示校核线或短连接线冒充马拉松路线。

## Web 前端与交互

页面采用三栏 GIS 工作台：

- 左栏按顺序呈现“起终点 → 选型目标 → 生成”，隐藏默认不需要调整的底层权重。
- 中间地图始终是视觉主区域。生成时显示阶段进度；生成后只绘制已通过质量闸门的路线，并自动适配视野。
- 右栏显示当前路线的质量闸门、关键指标、失败原因和认证免责声明。图层与服务诊断收纳进次级抽屉，避免抢占主流程。

交互规则：

- 默认起点和终点同址，用户可改为不同位置；地图选点后立即显示吸附位置和直线间距。
- 起终点间距超限时生成按钮禁用，并显示上限与当前值。
- 目标卡片缩减为三张，卡片文案明确“硬规则一致，仅排序偏好不同”。
- 生成按钮提供搜索、闭合、质量校验三个阶段状态，避免页面假死。
- 候选卡片优先显示里程、爬升、重复道路、自交和路网连续性，而不是泛化评分。
- 地图一次突出一条路线；其他候选弱化显示，避免多色线叠加造成误判。
- 桌面端保持三栏；中等宽度折叠右栏；移动端按地图、主操作、结果顺序纵向排列。

## 数据流与边界

`App` 只负责页面状态和异步生成流程。路线搜索、质量校验、目标排序和 UI 展示模型分别放在独立模块：

- `routeSearch`：从路网生成原始候选路径；
- `routeQuality`：计算并解释所有硬约束；
- `routeObjectives`：对合格路线按目标排序；
- `routePresentation`：把质量结果转换为界面标签和说明。

组件通过结构化结果传递数据，不解析算法日志。这样可以单独测试算法，也能替换未来的 iServer 网络分析服务。

## 测试与验收

### 自动化测试

- 为每条硬约束先写失败测试，再实现检查逻辑。
- 使用小型确定性图验证 Beam Search 不复用物理边、不反向折返、不自交，并在目标区间闭合。
- 使用真实武汉 GeoJSON 的回归测试，验证三个目标输出的所有路线都通过统一质量闸门。
- 组件测试覆盖起终点间距提示、禁用状态、三目标切换、生成阶段、无解提示和合规指标。
- 运行全量 `npm test` 与 `npm run build`。

### 可视化验收

在本地浏览器以桌面和窄屏视口逐个生成三个目标的路线并截图。每张路线需检查：

- 线条是否始终沿道路；
- 是否出现跨河/跨街直线、端点断裂或地图坐标漂移；
- 是否重走同一道路、原路折返、自交或形成局部绳结；
- 起终点和路线长度、坡度指标是否与质量面板一致；
- 多候选叠加是否导致视觉误判；
- 生成、错误、空状态和响应式布局是否清楚。

发现问题后新增回归测试并修复，重复生成和截图，直到三个目标均通过。截图保存到 `artifacts/route-qa/`，最终提交不包含临时调试文件。
